Guardian 在相關應用程式設定更新時先部署候選實例，使用 XHealth 驗證，再決定是否推廣。它依賴可靠的檢查定義，也需要伺服器有容量同時承載正式應用程式和候選資源。

## 啟用條件

- 應用程式使用無狀態部署方式；本地資料掛載應用程式不支援 Guardian。
- 已設定並驗證 XHealth，檢查能穩定判斷業務是否可用。
- 操作者具有 Operator 或 Admin 權限。
- 映像檔儲存庫、資源和調度條件允許候選實例執行。

在應用程式的 **XHealth** 頁面開啟 Guardian。首次啟用前先讓現有檢查通過，避免每次發佈都因檢查設定本身錯誤而失敗。

## 哪些變化會驗證

當前與 Guardian 相關的變化包括映像檔、容器執行參數、XConfig 和分組等設定。資源、連接埠、調度或其他字段的修改不能統一理解為一定建立候選發佈。

控制台不提供應用程式移動分組操作；接口能力與界面入口應分別看待。日常操作以儲存後應用程式概覽顯示的實際發佈狀態為準。

## 發佈過程

1. 編輯相關應用程式設定並儲存。
2. 應用程式概覽出現 Guardian 狀態，候選資源開始部署。
3. 候選實例就緒後執行設定的健康檢查。
4. 檢查通過後，平台將候選設定推廣給正式應用程式。
5. 等待正式副本完成更新，再驗證業務入口和執行狀態。

| 階段 | 應觀察的內容 |
| --- | --- |
| 部署中 | 映像檔拉取、資源、候選實例啟動 |
| 驗證中 | 檢查任務是否執行及輸出結果 |
| 失敗 | 錯誤原因、候選應用程式和檢查日誌 |
| 推廣中 | 正式副本替換和後續業務狀態 |

候選驗證成功不代表所有真實用戶端請求都已驗證，也不能替代資料庫兼容性評估。

## 驗證失敗後的操作

在狀態允許時，概覽頁提供以下操作：

- **重試**：修復臨時問題後重新執行驗證。
- **跳過**：由操作者明確接受風險，繞過檢查結果繼續推廣。
- **取消**：放棄尚可取消的候選發佈並清理相關資源。

跳過不是“檢查通過”。只有理解失敗原因且明確接受該設定時才使用。推廣階段或其他不可操作狀態下，部分按鈕不會出現，應等待狀態收斂後再判斷。

## 排障與限制

查看[應用程式日誌](/docs/zh-tw/guides/observability/logs/application/)時區分正式應用程式、Guardian 候選應用程式和 Guardian 檢查來源。候選映像檔無法執行、檢查工具缺失、目標連接埠錯誤和資源不足需要分別處理。

存在未完成候選發佈時，後續設定修改可能被拒絕。先處理當前發佈，再提交下一次變更。需要恢復已推廣的設定時，閱讀[回復與失敗處理](/docs/zh-tw/guides/release-safety/rollback/)。
