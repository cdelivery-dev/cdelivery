發佈失敗後，先確認失敗發生在哪個階段：候選設定尚未推廣、正式副本正在更新，還是更新完成後業務才出現問題。不同階段對應不同處理方式。

## 選擇處理方式

| 當前情況 | 首先考慮 |
| --- | --- |
| Guardian 候選檢查失敗 | 查看候選日誌，重試或取消候選發佈 |
| 更新暫停或失敗 | 檢查更新狀態、失敗動作及可用回復設定 |
| 新版本已執行但業務異常 | 評估上一份設定是否兼容當前資料，再決定回復 |
| 資料庫或外部資料已改變 | 使用相應資料恢復方案，不能僅依賴應用程式回復 |

取消候選發佈與撤銷已執行版本不是同一個操作。不要僅看到“失敗”就重複執行所有恢復按鈕。

## 執行回復

1. 以 Operator 或 Admin 打開應用程式概覽。
2. 記錄當前映像檔、錯誤和關鍵業務狀態。
3. 確認界面存在可用回復操作，並閱讀確認提示。
4. 提交後觀察回復狀態、實際副本和日誌。
5. 驗證業務入口、關鍵功能和 XHealth 結果。

平台使用當前可用的上一份部署設定，不提供任意歷史版本瀏覽器。沒有可用上一份設定時，需要使用儲存好的映像檔版本和設定重新部署。

## 回復策略

當前回復會並行處理全部副本，失敗動作是繼續；更新順序、觀察時間和失敗比例來自應用程式更新設定。它並不完全復用正向更新的並行度和失敗動作。

因此，即使正向更新按單個副本逐批執行，回復也不能被當作同樣節奏的逆向過程。應評估業務中斷和伺服器容量。

## 回復不會恢復哪些內容

- 資料庫寫入、遷移和資料格式變化。
- 外部 API 呼叫及其他系統的副作用。
- 被你另外刪除的資料卷或外部檔案。
- 任意久遠的歷史設定或映像檔。

舊程序可能無法讀取新程序已修改的資料。執行前需要明確這種兼容性，尤其是有狀態應用程式。

## 回復後仍異常

先確認回復是否真正完成，而不只是請求已接受。檢查原先的問題是否來自映像檔以外的因素，例如伺服器故障、資源不足、儲存庫連接或外部依賴。

回復設定本身也可能無法執行。此時保留錯誤和事件記錄，按[更新與重啟](/docs/zh-tw/guides/apps/lifecycle/)修正設定，或按資料恢復流程處理。不要把反復回復當作長期修復方法。
