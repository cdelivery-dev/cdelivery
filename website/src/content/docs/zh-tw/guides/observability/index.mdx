日誌、指標和事件回答不同問題。日誌解釋程序輸出，指標顯示隨時間變化的資源和請求情況，事件記錄平台觀察到的操作與執行變化。

## 選擇資料入口

| 需要回答的問題 | 頁面 |
| --- | --- |
| 程序為什麼啟動失敗 | [應用程式日誌](/docs/zh-tw/guides/observability/logs/application/) |
| 請求是否到達入口、回傳了什麼 | [存取日誌](/docs/zh-tw/guides/observability/logs/access/) |
| 應用程式是否受 CPU 或內存影響 | [應用程式指標](/docs/zh-tw/guides/observability/metrics/application/) |
| 某台機器是否資源不足 | [伺服器指標](/docs/zh-tw/guides/observability/metrics/server/) |
| 故障前發生過什麼變更 | [操作事件](/docs/zh-tw/guides/observability/events/) |
| 資料為何遲到或沒有儲存 | [採集與保留設定](/docs/zh-tw/guides/observability/settings/) |

Reader、Operator 和 Admin 均可讀取共享觀測資訊。設定 Insight、存儲和採集組件需要 Admin。

## 採集前提

伺服器和容器指標依賴採集組件；歷史觀測資料依賴 Insight 存儲。應用程式日誌還受所選日誌驅動影響，不能因為已啟用 Insight 就假設所有舊容器日誌都已經遷入存儲。

存取日誌來自 Pingress。繞過 Pingress、直接存取應用程式發佈連接埠的請求，不會自動出現在 Pingress 存取記錄中。

## 正確使用時間範圍

先選覆蓋故障發生時間的窗口，再逐步縮小。比較日誌、指標和事件時，確保它們針對同一應用程式、同一伺服器和相近時間。

大範圍圖表會按時間桶聚合，圖上的一個點不一定等於單次採樣。應用程式或伺服器剛建立、重新啟動、變更設定後，也可能尚無完整資料窗口。

預設伺服器採樣間隔為 5 秒，檔案系統採樣間隔為 5 分鐘。批量提交、寫入和不同實例之間的資料同步還可能帶來延遲，不能把採樣間隔直接當作頁面刷新保證。

## 沒有資料時

1. 核對目標對象和時間範圍。
2. 檢查 Insight 及採集組件狀態。
3. 檢查對應日誌驅動或 Pingress 是否實際產生該類資料。
4. 核對存儲連接和保留期限。
5. 查看頁面給出的查詢錯誤，區分查詢失敗和空結果。

空白或缺失資料不能證明系統健康，也不能單獨證明業務故障。應結合當前副本、檢查結果和實際存取再判斷。

## 建議的排障路徑

從事件定位變更時間，用指標確認影響範圍，再用對應日誌檢查具體錯誤。記錄你已經驗證的事實，避免僅憑同時發生就認定兩個現象存在因果關係。
