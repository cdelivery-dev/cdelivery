打開應用程式的日誌頁，先選擇正確的來源和時間範圍。應用程式、XHealth、XJob 與 Guardian 的輸出屬於不同執行資源，排查時不要把它們混在一起。

## 選擇來源

| 來源 | 用途 |
| --- | --- |
| 應用程式 | 正式應用程式進程的標準輸出和標準錯誤 |
| XHealth | 週期性檢查的執行輸出 |
| XJob | 某個計劃任務的輸出 |
| Guardian 應用程式 | 候選設定執行時的輸出 |
| Guardian 檢查 | 候選驗證任務的輸出 |

可用選項取決於實際存在的資源和日誌設定。歷史資源已經清理或日誌已經輪轉時，不一定還能查詢到原記錄。

## 查看步驟

1. 打開目標應用程式的日誌頁面。
2. 選擇對應來源；XJob 應明確到具體任務。
3. 選擇覆蓋問題發生時間的範圍。
4. 按頁面提供的條件篩選並翻頁。
5. 結合時間、來源和完整錯誤上下文判斷問題。

程序寫入容器內部普通檔案的日誌，不會自動等同於標準輸出日誌。需要在這裡查看時，應按應用程式自身的設定將所需輸出寫到標準輸出或標準錯誤。

## 日誌驅動

應用程式設定中可以選擇：

| 模式 | 行為 |
| --- | --- |
| 跟隨宿主機 | 使用宿主機當前日誌設定，保留和可讀取能力由該設定決定 |
| JSON 檔案 | 為容器日誌設定檔案大小和數量上限 |
| Insight | 將應用程式日誌交給 Insight，依賴對應服務和存儲 |

切換到 JSON 檔案時，界面初始值為每個檔案 10 MiB、保留 5 個檔案。檔案數量允許 1–100，每個檔案最大為 1 GiB。按業務日誌量調整，避免輪轉過快或佔滿磁盤。

修改日誌驅動會影響後續執行容器，不會自動補採之前丟失或已清理的日誌。

## 空日誌與查詢錯誤

沒有記錄時，先確認程序是否實際輸出到標準輸出、時間範圍是否正確、對應任務是否執行過，再檢查日誌驅動與採集服務。

查詢失敗時保留頁面錯誤資訊，檢查目標伺服器、存儲或組件狀態。不要把“查詢失敗”寫成“沒有錯誤日誌”。

查看早期故障時，還要考慮本地輪轉和 Insight 保留期限。歷史資料超出保留範圍後不能僅靠重新打開頁面恢復。

## 分享日誌

保留錯誤前後的必要上下文和時間，但移除存取權杖、密碼、使用者個人資訊及業務敏感內容。平台不能保證自動識別應用程式寫入日誌中的所有秘密。
