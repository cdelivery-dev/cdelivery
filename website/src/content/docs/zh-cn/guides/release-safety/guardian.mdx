Operator 和 Admin 可以提交应用更新或 PostgreSQL 变更，并处理未完成的发布。CDelivery 使用 [XHealth](/docs/zh-cn/guides/release-safety/xhealth/) 在预览实例上运行发布检查。

## 选择检查并提交

配置和示例见 [APP 依赖](/docs/zh-cn/guides/apps/dependencies/app/)和 [PostgreSQL 数据库依赖](/docs/zh-cn/guides/apps/dependencies/postgresql/)。

保存应用部署配置即可提交更新。镜像、环境变量、挂载、XConfig、资源、调度、网络、分组、凭据、日志、重启策略和更新策略等变化都可能触发检查；只改描述或副本数量不会触发。

**没有应用参与检查时，应用更新会直接上线，SQL 会直接在生产数据库执行。**

## 演练与上线

CDelivery 准备预览实例并运行所选检查。对于数据库变更，先在演练库执行 SQL，再检查应用。全部通过后，平台清理演练资源，包括演练库中的测试数据，再应用生产配置或在生产库执行同一份 SQL。

在预览实例中，指向本次变更目标的依赖会切换到预览连接，其他依赖沿用原连接。请为同时运行的线上应用和预览实例预留资源。

## 处理停止的变更

检查失败或执行中断时，变更保持未完成，平台保留诊断信息和剩余的临时资源。重试生产变更需要手动操作。可在应用的**概览 → 当前修改**或对应的依赖页查看详情，并查阅**预览应用**和**发布检查**的[日志](/docs/zh-cn/guides/observability/logs/application/)。

可用操作取决于变更停止时所处的阶段。

| 操作 | 结果 |
| --- | --- |
| 跳过检查并上线 | 清理演练资源，不再完成检查，直接应用生产变更 |
| 再次执行 | 重新执行生产变更。数据库变更会重新运行原始 SQL，请先核实上次执行的结果 |
| 确认完成 | 确认生产结果并完成清理，不执行 SQL，也不再次应用变更 |
| 取消 | 清理临时资源并关闭变更，已经执行的生产变更会保留 |

进入生产执行阶段前，可选择跳过检查或取消变更。若只剩清理工作，选择**确认完成**。如需重新演练，取消当前变更后重新提交。

## 完成与验证

未完成变更会占用所有参与应用，包括其他分组中的消费者。这些应用的配置更新、重启、回滚、删除和 XHealth 修改会被阻止，自动扩缩容也会等待。先处理当前变更，再提交冲突操作或手动删除其预览数据卷。

每个目标只保留最新一条变更。完成后检查线上副本和真实业务请求。[应用回滚](/docs/zh-cn/guides/release-safety/rollback/)恢复配置，不撤销 SQL，也不恢复数据库内容。
