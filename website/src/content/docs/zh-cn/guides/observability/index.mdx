日志、指标和事件回答不同问题。日志解释程序输出，指标显示随时间变化的资源和请求情况，事件记录平台观察到的操作与运行变化。

## 选择数据入口

| 需要回答的问题 | 页面 |
| --- | --- |
| 程序为什么启动失败 | [应用日志](/docs/zh-cn/guides/observability/logs/application/) |
| 请求是否到达入口、返回了什么 | [访问日志](/docs/zh-cn/guides/observability/logs/access/) |
| 应用是否受 CPU 或内存影响 | [应用指标](/docs/zh-cn/guides/observability/metrics/application/) |
| 某台机器是否资源不足 | [服务器指标](/docs/zh-cn/guides/observability/metrics/server/) |
| 故障前发生过什么变更 | [操作事件](/docs/zh-cn/guides/observability/events/) |
| 数据为何迟到或没有保存 | [采集与保留设置](/docs/zh-cn/guides/observability/settings/) |

Reader、Operator 和 Admin 均可读取共享观测信息。配置 Insight、存储和采集组件需要 Admin。

## 采集前提

服务器和容器指标依赖采集组件；历史观测数据依赖 Insight 存储。应用日志还受所选日志驱动影响，不能因为已启用 Insight 就假设所有旧容器日志都已经迁入存储。

访问日志来自 Pingress。绕过 Pingress、直接访问应用发布端口的请求，不会自动出现在 Pingress 访问记录中。

## 正确使用时间范围

先选覆盖故障发生时间的窗口，再逐步缩小。比较日志、指标和事件时，确保它们针对同一应用、同一服务器和相近时间。

大范围图表会按时间桶聚合，图上的一个点不一定等于单次采样。应用或服务器刚创建、重新启动、变更配置后，也可能尚无完整数据窗口。

默认服务器采样间隔为 5 秒，文件系统采样间隔为 5 分钟。批量提交、写入和不同实例之间的数据同步还可能带来延迟，不能把采样间隔直接当作页面刷新保证。

## 没有数据时

1. 核对目标对象和时间范围。
2. 检查 Insight 及采集组件状态。
3. 检查对应日志驱动或 Pingress 是否实际产生该类数据。
4. 核对存储连接和保留期限。
5. 查看页面给出的查询错误，区分查询失败和空结果。

空白或缺失数据不能证明系统健康，也不能单独证明业务故障。应结合当前副本、检查结果和实际访问再判断。

## 建议的排障路径

从事件定位变更时间，用指标确认影响范围，再用对应日志检查具体错误。记录你已经验证的事实，避免仅凭同时发生就认定两个现象存在因果关系。
