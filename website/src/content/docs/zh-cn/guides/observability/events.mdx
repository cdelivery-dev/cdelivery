事件记录平台观察到的操作和状态变化。它适合定位“问题前发生过什么”，但一条历史事件不能单独证明当前状态。

## 查看事件

打开应用的事件页面，选择问题发生前后的时间范围。查看事件时间、类型、对象、操作者以及详细信息，并与同一窗口的日志和指标对照。

例如新版本发布后出现失败，应先找到配置变更时间，再检查候选验证、正式副本替换及错误日志的先后顺序。

## 事件与诊断状态

| 信息 | 应如何理解 |
| --- | --- |
| 配置或生命周期事件 | 说明平台记录了某次操作或变化 |
| 运行异常 | 需要再查询当前副本和更新状态 |
| XHealth 失败 | 需要查看最近一轮检查的实际结果 |
| 恢复相关信息 | 应结合当前业务响应确认恢复 |
| 当前没有记录 | 不能据此认定系统完全正常 |

部分当前诊断记录存在内存中，与持久化事件历史并不是同一数据源。平台重启、保留期限和采集故障都可能影响可见记录。

## 定位操作者

事件中的来源有助于区分控制台、API 密钥、AI 对话或自动值班等触发方式。阅读时保留对象和时间上下文，不要仅凭一个显示名称推断全部权限或责任。

AI 值班可能在配置的角色权限内执行操作。需要检查它的行为边界时，参见[自动值班](/docs/zh-cn/guides/automation/duty/)及[角色与权限](/docs/zh-cn/administration/accounts/roles/)。

## 建立排障时间线

1. 记录用户首次报告问题的时间。
2. 查看此前的发布、重启、扩缩容和配置事件。
3. 核对相关应用及服务器的指标变化。
4. 查看同时间的业务、检查和访问日志。
5. 记录已经验证的恢复结果。

时间接近只说明相关性。外部依赖故障与应用发布可能同时发生，应通过实际请求和运行数据验证原因。

## 保留与分享

历史事件的可见范围受 Insight 存储与保留设置影响。重要问题处理完成后，可在你自己的事故记录中保存必要时间线和证据。

分享时保留事件类型、时间和必要错误，同时移除凭据和用户敏感信息。事件记录不是数据库备份，也不是任意历史配置的恢复入口。
