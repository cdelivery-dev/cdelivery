删除应用需要 Operator 或 Admin。删除会停止该应用提供的服务，适合永久下线或移除测试应用；需要暂时修复运行状态时，先考虑配置调整或重启。

## 删除前检查

1. 确认应用名称、所属分组及业务负责人。
2. 检查是否仍有客户端、其他应用或域名访问它。
3. 保存需要保留的配置源文件和版本信息。
4. 对有状态应用完成必要的数据备份。
5. 记录卷所在服务器、卷名称和容器内路径，便于之后识别保留数据。

如果需要保留任务或检查配置，应在删除前自行记录。删除不是导出或备份操作。

## 执行删除

打开目标应用，使用删除操作，并核对确认提示中的对象。提交后回到分组或应用列表，确认应用已移除，再检查外部访问是否符合预期。

底层容器和其他资源的清理可能是异步完成的。请求超时或报错时，先检查应用是否仍存在，再决定是否重试。

## 哪些内容会变化

| 内容 | 删除后的处理 |
| --- | --- |
| 应用及运行容器 | 移除应用，运行任务随后停止和清理 |
| XHealth | 随应用移除 |
| XJob | 随应用移除，不能继续执行该应用的任务 |
| Guardian | 相关候选验证资源被清理 |
| 分组 | 保留，不随单个应用删除 |
| 本地数据卷 | 保留，需要管理员另行管理 |
| 外部 DNS | 不会替你修改域名服务商中的记录 |

应用的域名路由随应用配置失去作用，但 DNS 仍可能指向 Pingress。下线完成后检查这些入口，避免遗留无效业务地址。

## 处理保留数据

在[数据卷管理](/docs/zh-cn/administration/nodes/volumes/)中确认数据所在服务器、卷大小及使用情况。只有确定不再需要数据并满足备份要求后，才删除对应卷。

XConfig 不作为长期归档保留承诺。即使某些日志、指标或事件仍在保留窗口内，也不能依赖删除后的应用入口长期访问它们。

## 同名重建

重新创建同名应用会产生新的运行资源和身份。历史日志、指标和旧配置不应被视为自动接续到新应用。使用原卷重建时，还需核对数据格式、凭据和镜像兼容性。

删除后出现持续访问请求时，检查 DNS、上游调用和监控配置，而不只是应用列表。
