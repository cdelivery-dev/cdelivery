副本设置决定应用需要运行多少个实例。修改需要 Operator 或 Admin。本地数据应用固定一个副本，不使用动态扩缩容。

## 固定副本

在应用配置中选择固定模式，填写期望数量并保存。副本数允许 1–65,536；实际能够运行多少仍受服务器资源及调度条件限制。

增加副本前确认应用支持并行运行：进程内会话、本地临时文件或重复消费任务，都可能需要应用自身处理。副本数不是数据库复制配置。

## 自动扩缩容

选择动态模式，设置最小和最大副本数。最小值至少为 1，最大值不能小于最小值。未填写最大值也不表示可以突破平台上限、资源或调度约束。

自动判断依赖有效的 CPU 采样。先在 [Insight 设置](/docs/zh-cn/guides/observability/settings/)中确认采集组件工作，并检查现有副本都已运行。

| 当前行为 | 说明 |
| --- | --- |
| 评估周期 | 通常每 30 秒检查 |
| 采样窗口 | 至少 60 秒，并随采样间隔调整 |
| 扩容方向 | CPU 利用率超过 70% 时评估扩容 |
| 目标利用率 | 按约 60% 计算所需副本 |
| 缩容方向 | 低于 50% 持续至少 5 分钟后评估 |
| 数据不足 | 保持当前数量，等待有效样本 |

这些条件共同决定调整，并不保证到达某个时间点就立即增加或减少副本。部署、配置变化、样本不完整和容量不足都可能使控制器等待。

## CPU 限制的影响

配置 CPU 限制时，应用负载按该限制解释。未设置限制时，计算会考虑服务器 CPU 核数，扩容容量判断也更保守，不应期待在同一台服务器上持续增加未设 CPU 限制的副本。

希望在同一服务器运行多个自动扩容副本时，应设置合理的 [CPU 限制](/docs/zh-cn/guides/apps/resources/)，同时确认每台服务器的副本上限允许这种分布。

## 验证和排障

1. 保存动态范围，等待初始副本稳定运行。
2. 检查指标是否持续更新，所有运行副本是否都有有效采样。
3. 在可控测试负载下观察期望副本和实际副本。
4. 对照调度标签、资源预留和每服务器上限检查可用容量。

负载较高却未扩容时，依次检查采样、正在进行的更新、当前最大值和服务器容量。负载降低后未立即缩容通常需要等待持续低负载窗口；频繁改配置会影响观察窗口。

切回固定模式后，由你明确指定副本数。更改策略后仍应观察业务错误率和延迟，不能只根据副本数量判断效果。
