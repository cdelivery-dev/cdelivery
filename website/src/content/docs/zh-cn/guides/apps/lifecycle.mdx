更新和重启需要 Operator 或 Admin。执行前先检查应用状态及是否有正在进行的 Guardian 验证，避免把多次操作叠加在未完成的发布上。

## 选择合适操作

| 目标 | 使用方式 |
| --- | --- |
| 修改镜像、环境变量或其他设置 | 编辑配置并保存 |
| 使用当前配置重新创建运行容器 | 重启 |
| 撤销可用的上一份部署配置或候选发布 | [回滚与失败处理](/docs/zh-cn/guides/release-safety/rollback/) |
| 彻底移除应用 | [删除应用](/docs/zh-cn/guides/apps/delete/) |

重复保存未变化的配置不会强制更新容器。同名镜像标签在仓库中发生变化，也不会自动触发发布；业务版本更新应使用可识别的新标签。

## 更新配置

1. 记录当前镜像版本及关键设置。
2. 编辑需要改变的字段，保留不需要改变的配置。
3. 核对更新顺序、并行度及容量。
4. 保存后查看应用概览与事件。
5. 等待实际副本稳定，再检查日志、XHealth 和业务入口。

镜像、容器参数、配置文件等相关变化在启用 Guardian 时可能进入候选验证流程。并不是所有字段修改都会创建候选发布，具体见[发布验证](/docs/zh-cn/guides/release-safety/)。

## 重启应用

重启会要求运行容器按当前配置重新创建，并使用应用更新策略。它不是单纯向原进程发送一个信号，也不修改数据库已经写入的数据。

默认更新策略会并行处理全部副本，并先停止旧副本。需要保持连续访问时，先评估[更新策略](/docs/zh-cn/guides/release-safety/update-strategy/)、额外容量及应用是否允许并行运行。

单副本应用重启可能中断连接。本地数据应用应先检查备份和数据库停止要求。

## 操作完成的判断

保存或重启请求成功后，还需确认：

- 实际副本数量符合期望。
- 没有持续等待、失败或重启的容器。
- 新容器日志没有启动错误。
- 业务请求和相关健康检查正常。
- 如果使用 Guardian，候选验证与推广已完成。

发生错误时，先判断操作是否已部分生效，再决定重试、修正配置或回滚。连续点击重启会增加判断运行状态的难度。

## 回滚的边界

回滚依赖当前可用的上一份配置，不提供任意历史版本选择。它不能撤销数据库迁移、外部服务调用或已写入的数据。

还应注意回滚执行策略与正向更新并非完全相同：当前回滚并行处理全部副本，失败动作是继续。完整说明见[回滚与失败处理](/docs/zh-cn/guides/release-safety/rollback/)。
