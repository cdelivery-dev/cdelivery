Operator と Admin はアプリの更新や PostgreSQL の変更を申請し、途中で停止した変更に対処できます。CDelivery は [XHealth](/docs/ja/guides/release-safety/xhealth/) を使ってプレビュー環境でリリース検証を行います。

## 検証対象と送信

設定手順と例は[アプリ間の依存関係](/docs/ja/guides/apps/dependencies/app/)と [PostgreSQL の依存関係](/docs/ja/guides/apps/dependencies/postgresql/)を参照してください。

アプリのデプロイ設定を保存すると更新を送信できます。イメージ、環境変数、マウント、XConfig、リソース、配置、ネットワーク、グループ、認証情報、ログ、再起動ポリシー、更新方式などの変更が検証対象になります。説明やレプリカ数だけの変更では検証しません。

**参加するアプリがなければ、アプリの更新はそのまま本番に適用され、SQL は本番データベースで直接実行されます。**

## 検証と本番適用

CDelivery はプレビュー環境を準備し、データベースの変更であれば検証用データベースに SQL を適用してから、選択された検証を実行します。すべて成功すると、検証用データベースへの書き込みも含めて検証用リソースを削除します。その後、アプリの設定を本番に適用するか、本番データベースで同じ SQL を実行します。

プレビュー環境では、変更対象への接続だけがプレビュー用に切り替わります。それ以外の依存先には元の接続を使います。本番アプリとプレビューを同時に動かせるだけのリソースを確保してください。

## 停止した変更の処理

検証に失敗したり実行が中断したりすると、変更は未完了のまま残ります。診断情報と残りの一時リソースは保持されます。本番で再実行するには手動での操作が必要です。アプリの**概要 → 現在の変更**または該当する依存先のページで詳細を開き、**プレビューアプリ**と**リリース検証**の[ログ](/docs/ja/guides/observability/logs/application/)を確認してください。

選べる操作は、変更が停止した段階によって異なります。

| 操作 | 結果 |
| --- | --- |
| 検証を省略して適用 | 検証用リソースを削除し、検証を完了せずに本番へ適用 |
| 再実行 | 本番で変更を再実行します。データベースの変更では元の SQL をもう一度実行するため、先に前回の実行結果を確認してください |
| 完了を確認 | 本番の結果を確認して後片付けを完了。SQL や変更は再実行しない |
| キャンセル | 一時リソースを削除して変更を閉じる。適用済みの本番変更は維持 |

本番適用前なら、検証を省略するか変更をキャンセルできます。後片付けだけが残っている場合は**完了を確認**を選びます。検証をやり直すには、現在の変更をキャンセルしてから再度申請してください。

## 完了と確認

未完了の変更は、ほかのグループの利用側アプリも含む参加アプリを占有します。設定更新、再起動、ロールバック、削除、XHealth の変更は拒否され、自動スケーリングも待機します。競合する操作やプレビューボリュームの手動削除の前に、現在の変更を処理してください。

各対象には最新の変更だけが保存されます。完了後は本番レプリカと実際の業務リクエストを確認します。[アプリのロールバック](/docs/ja/guides/release-safety/rollback/)は設定を復元しますが、SQL の取り消しやデータベース内容の復元は行いません。
