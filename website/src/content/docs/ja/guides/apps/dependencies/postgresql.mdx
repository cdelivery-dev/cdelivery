このデータベースを依存先として直接参照するアプリは、[XHealth](/docs/ja/guides/release-safety/xhealth/) で**リリース検証に参加**を有効にできます。たとえば注文サービスなら、データベースの変更後も注文照会で期待どおりのデータを取得できるか検証します。

## データベースを登録

- [Neon](/docs/ja/guides/apps/dependencies/postgresql/neon/) — Neon の接続を登録し、検証用ブランチのコンピュートサイズを選びます。
- [PlanetScale](/docs/ja/guides/apps/dependencies/postgresql/planetscale/) — PlanetScale の PostgreSQL 接続を登録し、検証に使うデータの復元時点とサイズを確認します。
- [ローカル PostgreSQL](/docs/ja/guides/apps/dependencies/postgresql/local/) — 既存の PostgreSQL アプリを登録し、ZFS ボリュームのクローンで変更を検証します。

## アプリから参照

Admin がプロバイダー別の手順に従って既存の本番データベースを登録します。Operator または Admin はアプリの環境変数 `DATABASE_URL` に依存先の `dsn` を指定し、確定して保存します。個別の接続パラメーターを使う場合は `host`、`port`、`database`、`username`、`password` を対応する変数に割り当てます。

## SQL の変更を検証する

PostgreSQL の依存先を開き、**変更を作成**を選んで SQL を入力します。クラウドデータベースの場合は検証用ブランチのサイズも選べます。SQL は入力したとおりに実行され、トランザクションは自動で追加されません。

**検証に参加するアプリがない場合、変更を送信すると SQL は本番データベースで直接実行されます。**

参加するアプリがある場合、CDelivery はまず検証用データベースで SQL を実行します。次に各アプリのプレビューをそのデータベースに接続し、業務フローを検証します。いずれかの検証に失敗すると変更はそこで止まり、本番のアプリは元のデータベースを使い続けます。すべての検証に成功すると、CDelivery は検証用リソースを削除してから、本番データベースで同じ SQL を実行します。

変更が停止した場合のログの場所と対処は[リリース検証](/docs/ja/guides/release-safety/guardian/)を参照してください。

## 置き換えと削除

登録済みのデータベース接続設定は編集できず、保存した認証情報や DSN の表示・ダウンロードもできません。接続や認証情報を変更する場合は、新しい依存先を登録してアプリの選択を切り替えます。

Admin は未使用の依存先を削除できます。現在の参照、まだ利用可能なロールバック設定、未完了の変更があると削除できない場合があります。削除するのは登録と認証情報であり、データベースではありません。ローカルのデータベース依存先が存在する間、その元アプリの削除や別グループへの移動はできません。
